Developer and operator manual

ai-devpack reference

Run, inspect, extend, and release the automotive C/C++ development harness.

1. Overview

The pack gives small and on-premises agents bounded tasks backed by deterministic checks. The orchestrator can prepare work and request execution. Trusted gate commands and independent review authorize progress. Missing or invalid evidence fails closed. Fix attempts are bounded and unresolved work goes to a human. Merge and safety decisions remain human responsibilities.

Obtain data-owner sign-off before use. Classifications in increasing order are public, internal, confidential, customer-restricted, and secret. Engine routing checks the configured ceiling and refuses secret data. Retention, customer permission, and approved service decisions remain operator obligations. Treat run artifacts at the source classification. See policy/data_governance.md and policy/asil_boundaries.md.

Brief
A bounded task with goals, inputs, outputs, scope and verification commands.
Engine
A configured model and invocation protocol.
Gate
A trusted set of checks whose receipt records individual outcomes.
Checkpoint
A recorded policy or human decision tied to a subject and evidence.
Oracle
A human-authored clarification for an eval task. Hidden graders check the result independently.
Component
A named subtree selected within the configured source workspace.

2. Architecture

orchestrator/ provides orchestration instructions and example briefs. workflow/templates/ supplies implement, review and fix briefs, a task plan, an ADR and a dependency-plan example. runner/devpack_run.py coordinates a whole task. runner/devpack_dispatch.py routes individual roles and records guarded attempts. runner/devpack_submit.py validates broker submissions. runner/devpack_broker.py services the queue on the trusted host, validates worktree and brief boundaries, and executes through the runner adapter.

runner/agent_exec.py loads engines, checks classification and isolation, constructs argv and mounts, and normalizes execution evidence. Native cloud and local engines share a CLI protocol. An external engine uses operator-supplied argv and a declared result protocol. Worker edits are bounded to allowed brief paths and any active component scope. Keep pack code, grading inputs, trusted Git metadata, approval state, and the gate configuration out of worker control. Scope and test-lock checks compare actual changes to trusted input. Sandbox containment, post-run verification and classification are distinct controls.

runner/workspace_scope.py resolves components, built-in exclusions and selected scans. runner/safe_git.py protects Git operations from untrusted settings. runner/repomap.py generates a budgeted C/C++ index. runner/memory.py recalls scoped, bounded memory and validates proposals. Learning mines evidence and qualifies engine guidance. Dashboards consume recorded artifacts. Eval isolates benchmark fixtures and grades against trusted harness inputs.

3. Workflow

Lint the brief against the repository and engine budget. The broker treats structural findings in orchestrator briefs as errors. Human-authored brief findings are advisory at lint time. Parse the allowed files, baseline protected tests and run the implementer with a bounded prompt. The host checks changes, runs the gate, and sends evidence and the diff to the reviewer after a pass. The reviewer supplies exhaustive findings and a final verdict. Retry eligible failures with a fix brief and rerun checks. Scope, test integrity, broken harness prerequisites and human-owned decisions can stop progress early. The configured maximum is capped at two fix rounds unless a registered deviation applies.

In hitl mode, requested checkpoints require a human decision. In autonomous mode, eligible checkpoints can be auto-approved under policy and evidence validation. Blocking checkpoints cover plan, brief, deviation and SELinux manifest decisions. Their callers can pause before advancing. A paused task returns 20 and records AWAITING_APPROVAL and an approval ID. Terminal checkpoints such as pre-merge, escalation and decision memory record the decision boundary after work. A pending terminal decision does not provide a worker continuation. Protected or unknown merge targets, escalation, decision/fact memory, safety- or security-relevant deviations, high/unknown ASIL deviations and release SELinux manifests require human approval as applicable to the checkpoint.

Inspect the approval record and evidence using runner/devpack_approve.py. Approve or reject with an operator note where required. Resume the same runner or dispatch with the recorded ID and matching workdir/state directory. Resume verifies saved inputs and consumes an approved continuation once. A changed brief requires a fresh approval. Provenance goes to trusted JSONL and, where applicable, Git notes. See runner/checkpoints.py and policy/operating_modes.md.

Plans declare a DAG of task IDs and Markdown briefs. runner/devpack_plan.py validates schema, reads briefs and checks dependencies. Its run-next selects one ready task from recorded attempts and delegates to the task runner. Inspect plan status before retrying a failed prerequisite. A separate human decision handles merge.

Use log analysis to identify BRIEF (bad input), CONTEXT (missing repository knowledge), SKILL (missing or wrong guidance), TOOL (harness or permissions), MODEL (incorrect result under adequate conditions), or ENV (infrastructure or quota). A primary and optional secondary label support the handoff. Confirm heuristic findings through the logs CLI and use the evidence to fix the brief, routing, tool or environment before trying again.

4. Runs and logs

Run data is written below the configured runs root. This tree uses placeholders for generated names.

runs/<run-id>/
  run.json                       identity, outcome, timing and step index
  heartbeat.json                 liveness and current phase for active work
  steps/
    NN-role-engine.prompt.md     prepared prompt
    NN-role-engine.jsonl         normalized or provider stream events
    NN-role-engine.meta.json     step status, timing and measured usage
    NN-gate.txt                  captured gate output
    NN-gate-receipt.json         structured receipt when supported
  run_summary.json               task runner result and checkpoint summary
  attribution.json               optional heuristic and confirmed causes

Artifact names vary by entry point and protocol. A legacy log directory can also receive summaries. The logs CLI renders a Markdown transcript and standalone HTML, or analyzes failure signals. runner/redaction.py masks configured secrets and sensitive values before logging and rendering. Redaction complements storage and access controls. The runner heartbeat is a liveness claim with timestamps and phase, distinct from a test receipt or a terminal outcome.

The CLI and TUI use runner/dash/reader.py to assemble snapshots from run records, step streams, gate receipts, broker queue records, plans and external approval state. runner/dash/files.py handles constrained file reads and runner/dash/events.py normalizes events. The reader refreshes active jobs more often than discovery, bounds history, and reports source health. Use the TUI for interactive views and the CLI for text and JSON snapshots. Keep dashboard configuration in trusted operator space.

Engine configuration

Use runner/engines.example.toml as the starting point. version is integer 2 for named engines. roles maps role to engine name. Legacy inline role definitions support model, cmd and timeout_s. gate_cmd is an argv array and gate_timeout_s is an integer defaulting to 300. Both can appear under limits as fallback. Gate, plan and dashboard

Gate TOML requires at least one [[check]] table. Each has a unique nonempty string name, nonempty string array cmd, positive numeric timeout_s (300 by default), and boolean required (true by default). Commands run in the selected gate directory and support {pack_root}. Required command failure stops the gate. Optional failures are recorded. See enforcement/gate/gate.project.example.toml and enforcement/gate/gate.example.toml.

[[check]]
name = "build"
cmd = ["cmake", "--build", "build"]
timeout_s = 600
required = true

The plan file requires string id, title, goal, ISO date or timestamp created, and [[tasks]] entries. Optional string owner_role renders as Unassigned when absent. Each task needs unique string id, string title, contained Markdown path brief and string array depends_on (use [] for roots). Optional string role, positive integer size_limit, and string array requirement_ids provide task metadata. See workflow/templates/plan.example/plan.toml.

Dashboard settings are supplied via an explicit operator TOML outside the workdir and artifact roots. runs_root, plans_root, and engines_config are paths. Runs defaults to runs. Plans falls back to the project setting or plans. Engine settings use the project engine configuration, a conventional project file or the pack example. log_roots and evidence_roots are path arrays defaulting to empty. Relative paths resolve under workdir. The remaining settings are positive integers.

6. CLI reference

Run these examples from the pack checkout. Per-command tables list top-level options and subcommand options separately. Use the relevant subcommand's help for ordering. A successful operation typically returns 0 and argparse misuse returns 2. Gate returns 1 for invalid configuration or a failed required check. The SELinux source and linked-policy gate returns 1 for findings and 3 for incomplete evidence. Other tools document their command-specific result in the surrounding workflow. Task execution returns 1 on escalation or other task failure and 20 on a blocking approval. A terminal approval can be pending after task execution completes. Plan run-next returns 1 when no task is ready and work remains. Dashboard queries can return 1 for unavailable sources and invalid options return 2. Engine timeouts and launch failures can be represented as 124 and 126/127 in step results. Inspect the run outcome and receipt as well as the process status.

8. Quality gates and eval

tests/run_all.sh runs unittest discovery across pack subsystems and skill test directories and shellchecks scripts when shellcheck is installed. The full pack gate also checks offline evaluation fixtures, graders, skill lint, example briefs, repomap, log rendering, C/C++ lint and cppcheck. Use verified test completion evidence where required.

Protect the expected output, assertion behavior and preprocessing of protected tests. Evidence collection gathers artifacts for later inspection. 9. Extending the pack

Add an engine or adapter

Declare an engine, route the intended role, and set its data ceiling, timeout, context and isolation. Keep credentials in allowed operator environment variables. Run offline contract tests with a fake engine and fixture artifacts before qualifying it. For external adapters, install the executable in the approved execution environment. command is argv with a literal executable. Templates support {brief} (prompt file), {workdir}, {role} (mapped role), {model}, {run_dir} (adapter outputs), and {allow_args} (argv splice occupying an entire argument). The engine identity uses agent:model. The adapter example and offline fixture are in runner/engines.example.toml and runner/tests/fixtures/external_job.py.

[engines.worker]
class = "external"
model = "worker:standard"
command = ["job-runner", "{brief}", "{workdir}", "{role}", "{run_dir}", "{allow_args}"]
result = "json-stdout"
reply_from = "json:reply_path"
events_from = "{run_dir}/events.jsonl"
env_allow = ["JOB_RUNNER_TOKEN"]
max_data_class = "internal"
timeout_s = 900
[engines.worker.role_map]
implementer = "implement"

For json-stdout, emit one JSON object with string status and integer exit_code. Optional agent/model identity must match configuration. Supply a relative reply_path for json:reply_path. The executor consumes optional usage.input_tokens, usage.output_tokens, measured cost (total_cost_usd, cost_usd or cost) and reviewer verdict. Recognized external statuses are ok, failed, timeout, gate-failed, exhausted, quota, quota-exhausted and engine-unavailable. Other values classify as a harness error. Use APPROVE or REQUEST_CHANGES for a successful reviewer response. A status of ok with a nonzero process or reported exit fails. exit-code mode uses process status. Reply sources also include stdout and file:relative-path under the adapter output root. The optional events file is tailed through the executor, which bounds and redacts input. Keep it and reply files within the declared output boundary.

{"status":"ok","exit_code":0,"agent":"worker","model":"standard","reply_path":"reply.md","usage":{"input_tokens":104,"output_tokens":32}}

Add a gate check

Add a deterministic command with a unique name to trusted gate TOML. Keep operator check code and its configuration outside worker write scope. Provide a timeout and verify both pass and failure receipts. For component checks, obtain active scope through the existing workspace APIs.

Add a skill or eval task

Write trigger and contract in a skill's SKILL.md and keep detailed reference material next to it. Add isolated skill fixtures, expected outputs and graders. Run skill lint before model trials. For an eval task, provide task.md, seeded and solution patches, and check.sh, with hidden cases and an oracle where appropriate. Add negative controls and verify them offline. Follow eval/README.md and skilltest/README.md.

Add a dashboard view

Build a projection from the shared Reader snapshot, use constrained artifact reads, and reuse the common event normalizer and presentation helpers. Keep commands that mutate approvals in the approval CLI. Test unknown, missing, stale and malformed sources with fixtures before wiring the view into the CLI or TUI.

11. Operations and troubleshooting

SymptomWhat to inspect and do
Scope violationInspect the actual changed paths, brief globs and active workspace components. Remove unrelated edits or have the human revise and reapprove the scope.
Test-lock violationCompare test files against trusted baseline. Restore protected tests. Request a registered deviation if the test contract legitimately changes.
Gate failedOpen the first failed required check in the receipt. Reproduce that command using the same trusted config, baseline and component set. Fix the product or repair missing proof before rerunning review.
Quota or engine unavailableCheck the step status and sanitized stderr. Verify credentials presence, configured executable, budget, context and classification. Treat infrastructure failure separately from output quality.
AWAITING_APPROVALRead the approval evidence and inspect the checkpoint ID. Decide in the approval CLI using trusted state. Resume only a blocking continuation using its recorded ID.
Quiet or stale heartbeatCompare its timestamp and phase with the actual runner or broker process. Check for timeout or worker loss before retrying. A quiet run can still have a live process.
Dashboard missing artifactsVerify roots and coverage, then check symlinks, permissions and source health. Use CLI output if Textual is unavailable.

12. Known gaps

  • The README describes Python 3.10+ support. enforcement/gate/gate.py imports stdlib tomllib directly, so run the full gate with Python 3.11 or newer.
  • .devpack/project.example.toml says allow_unsandboxed_local permits local isolation. runner/agent_exec.py records that worker-project value as ignored. Use trusted authorization.
  • The future adapter and accounting sections in docs/design/dashboard.md are design material. The shipped reader joins pack-shaped artifacts. It has no general external job discovery or accounting integration.
  • runner/devpack_dash.py defaults to runs even if the project has a different runs root. Set the dashboard root explicitly when runner output is redirected.
  • knowledge/skills/telaf-selinux/references/example-platform-profile.toml includes contexts and build makefile conventions. knowledge/skills/telaf-selinux/scripts/platform_profile.py validates the required profile subset and does not retain these fields in its normalized profile.
